# Agent Note: M0 脚手架——8-workspace 边界先行
Status: superseded
Superseded by: [2026-09-26-align-with-upstream-spec.md](../../accepted/architecture/2026-09-26-align-with-upstream-spec.md)（M0.6 对齐官方 SPEC：本 note 的协议栈 workspace 边界已整体删除，原文保留不改写）

## Problem

symphony-ts 要在 TypeScript 中重实现 OpenAI Symphony（Rust）：协议（sym/0）、转码、可靠传输、网关、插件、relay、CLI、示例。上游是单一语言多 crate 工程，wire 协议细节（protobuf 字段、常量、握手时序）需要先对照上游校准，短期内无法直接写出可运行的完整协议栈。冷启动时若把所有逻辑堆在一个包里，后续拆分成本会随代码量指数上升；Agent 协作也需要稳定的"改哪里"边界。

## Decision

M0 只固化边界，不实现完整协议：按上游 crate 职责拆成 8 个 npm workspace（sym / proto / transport / gateway / plugins / relay / ctl / examples），每包给出类型骨架 + 公共 API + 单测；未实现的能力用**显式 throw 的占位函数**表达（如 `sym.encode/decode`、`WsTransport`），而不是静默 no-op。依赖方向随上游数据流固定：`sym` ← `transport`/`proto` ← `plugins` ← `gateway` ← `examples`。构建 / 测试 / lint 全绿作为 M0 验收。

## Alternatives considered

- **单包起步、M1+ 再拆**：迭代最快，但 wire 模型、传输、网关耦合在一个 API 面里，M2/M3 拆包时要动所有 import 与测试；且"扩展点表"无从谈起，Agent 冷启动只能读全部代码。否。
- **先实现完整协议再分包**：协议细节依赖对上游 Rust 代码的逐字段校准（M1 的工作），提前实现等于把校准成本乘 8。否。
- **每个里程碑动态调整包结构**：包边界频繁变动会让 README / Note / 测试位置全部漂移，协作成本高于收益。边界一次定准、变更走 Note 流程。否。

## Consequences

- 正面：M1+ 每个里程碑都有明确落点包；占位 throw 让"未实现"在运行期显式暴露，不会被误当成能力；文档（AGENTS.md 扩展点表、docs/architecture.md 依赖表）与包结构一一对应。
- 负面 / 承诺：8 个包在 M0 存在大量骨架代码，读起来"薄"；包边界一经接受不得随手改——调整包结构、依赖方向、`Message` 模型都必须先写新 Note；占位函数在对应里程碑必须被真实实现替换，不允许长期以 throw 形态存在（各包 README 的 Known limitations 是追踪清单）。
