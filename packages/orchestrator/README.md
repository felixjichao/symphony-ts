# @symphony/orchestrator

## Purpose

SPEC **§7 Orchestration State Machine**、**§8 Polling, Scheduling, and Reconciliation**、**§14 Failure Model and Recovery Strategy** 的 owner 包，对应 §3 的 Orchestrator：轮询节奏、claim 集合、并发上限、dispatch 排序、retry / backoff、reconciliation，以及"单一权威 orchestrator runtime state"的维护。**修改 retry policy 的唯一落点在本包。**

M5.1 已落地**纯调度内核**（无副作用）：`createOrchestratorRuntimeState()` 初始化单一权威 runtime state；`DispatchPolicy` + eligibility 纯函数负责 active / terminal state、required-label matching、`issue_routable`、dispatch eligibility、claim / running gating、global / per-state 并发 slot；`sortForDispatch()` 实现 §8.2 stable sort；`backoff.ts` 提供 continuation / failure retry 的纯数学延迟。该内核不 fetch tracker、不 spawn worker、不调用 workspace cleanup、不解释 agent / Codex 协议。

M5.2 已落地 **dispatch + worker lifecycle**：`OrchestratorAuthority` 是单一写入者，`dispatchIssue()` 在 `claimed` + `running` 双检查后于无 `await` 的提交段原子写入 `running` + `claimed`、清除同 issue retry entry 与 timer；`WorkerControl` 提供幂等的 `stop(reason)` 与 attempt `AbortSignal`，并等待 runner 真正收尾；`runAgentAttempt()` 的正常 / 异常结果都经统一 `completeAttempt()` 归约为终态 `RunAttempt.status`（`outcome.ts`，主动 stop reason 优先于底层 `port_exit`）；`applyAgentEvent()` 只消费稳定 `AgentEvent`，以 **thread 身份为隔离边界**（异 thread 的无关 / 迟到遥测丢弃）、**thread owner 与 turn 身份都只由可靠生命周期事件确认**（`other_message` / `malformed` 等诊断事件即使先到也不得抢占尚未确认的 owner；`notification` 等携带的 turn id 不改写身份），身份未齐时把 usage / PID / last event 暂存在 per-attempt 遥测里（usage 到达即按**所属 thread 各自的基线**入账，取得完整身份后回填 `LiveSession`；候选切换 / owner 确认都保留每个 thread 已计入的额度，A→B→A 交错绝对快照不重复入账）；`createTrackerRefreshContinuationDecider()` 注入同线程 continuation 判定与 tracker refresh。`@symphony/agent` 增加最小 `signal` / `onPhase` 契约以支持取消，取消覆盖 launch 前 / 握手中 / turn / continuation / 收尾。

M5.3 已落地 **retry 队列 / timer 所有权 / backoff 决策**（SPEC §8.4、§14.2、§16.6、§17.4）：`OrchestratorAuthority` 在 worker 终态归约后按 `retryKind` 建立完整 `RetryEntry`——normal exit 固定 `attempt = 1` / `1000` ms / `error = null`，abnormal exit `attempt = (RunAttempt.attempt ?? 0) + 1`、`delay = min(10000 * 2^(attempt - 1), agent.max_retry_backoff_ms)`（每次新建从当前 effective cap 读取）；`scheduleRetry()` 取消 / 替换同 issue 旧 timer，claim 保留为 `RetryQueued`。timer 端口（`RetryScheduler`，默认 `setTimeout` 实现）与单调时钟均可注入；每次排队分配独立 ownership token，**timer 回调只提交带 issueId + token 的到期事件**，stale / canceled / 被替换的迟到回调被 token 隔离，绝不重复派发。retry timer 到期完整执行 §16.6 `on_retry_timer`：pop entry → `fetch_issues_by_ids` refresh → fetch 失败（保留 claim，`retry refresh failed` 重排）/ missing（释放 claim）/ terminal（经注入的 `cleanupWorkspace` 安全清理 + 释放）/ inactive·unroutable（释放、不 cleanup）/ slot 不足（`no available orchestrator slots` 重排）/ active+routable（用 entry.attempt 重新 dispatch）。重派经 authority 内部提交路径消费自己的 claim，普通候选 dispatch 不豁免 claim。terminal cleanup 的 `refused` / `failed` / 异常只经 `onDiagnostic` 暴露且释放 claim，本包不做删除 fallback；cleanup 是异步删除，因此 authority 用 `cleanupInFlight` 把同 issue 的 cleanup 与后续 refresh / launch **串行化**——删除在途时新 retry 必须先等待并重新校验 ownership，避免新 worker 写入随后被删的 workspace。默认 `createRetryScheduler()` 对超过 Node `setTimeout` 上限（`RETRY_MAX_TIMER_DELAY_MS = 2^31 - 1`）的合法 backoff 采用**分段 timer**，保持规定延迟而非被压成 1 ms。真实链路（`runAgentAttempt` → app-server fixture subprocess → outcome → fake timer → refresh → 新 worker）用两次 attempt 的不同 PID / `cwd === workspace.path` / 退出存活检查与 workspace marker 内容保留，验证新 subprocess session 与 workspace 复用。

M5.4 已落地 **active-run reconciliation / stall detection / terminal cleanup / startup terminal sweep**（SPEC §7.3 / §7.4、§8.5 / §8.6、§14.2 / §14.3、§16.3、§17.4）：`OrchestratorAuthority.reconcileRunningIssues()` 严格按 SPEC 先做 Part A stall、再做 Part B 批量 refresh。stall 判定抽成 `src/reconciliation.ts` 纯函数：基准是**同一 UTC 墙上时钟域**的 `entry.session.lastCodexTimestamp ?? telemetry.pendingLastTimestamp ?? attempt.startedAt`（身份未齐的暂存时间戳也推进活动时间），`max(now - baseline, 0)` **严格大于**阈值才触发；`stallTimeoutMs <= 0`（或非有限值）整体禁用；触发后只以 `{ kind: "stall" }` 停止 worker，`stalled` 终态与一次 failure retry 由既有 `completeAttempt()` 建立（不手动排第二次）。Part B 在 Part A 完成后按**当前仍在 running** 的集合取剩余（stall 收尾期间自然退出 / 被替换的 worker 不参与本次 fetch），**剩余为空时零 tracker 请求**；否则 fetch 前捕获每个 issue 的 attempt token、一次 `fetchIssuesByIds(runningIds)` 批量 refresh；失败保留 worker（§14.2）；只处理本次请求的 ID（额外返回记录忽略）；active + routable 更新 running entry 的完整 issue snapshot；terminal → stop（`{ kind: "terminal" }`）+ 安全 cleanup；active 但 unroutable / 非 active 非 terminal / missing → stop（不 cleanup）。cleanup 端口从 `RetryOptions` **提升为 authority 顶层 `cleanupWorkspace`**（未提供时回退旧接线），因此 terminal cleanup 不再依赖是否启用 retry；per-issue 收尾屏障（`withCleanupBarrier`）覆盖"从请求 stop 到删除完成"的整个窗口并与后续 refresh / launch 串行化，terminal 的"屏障 → stop → outcome/after_run → removeWorkspace"次序确定。refresh 结果在写入前回校验 per-issue **reconciliation epoch**（重叠调用按发起顺序决胜，较晚发起的调用结果不被较早调用的迟到结果回退）与 **lifecycle generation**（`commitDispatch()` 每次派发递增并跨退出 / retry 保留）；被更新生命周期接管的结果整条丢弃——即使新生命周期也已退出并留下自己的 retry，也绝不误取消；仅当两者都不变、原 attempt 已自然退出且判定 stop 时才取消该旧生命周期 retry 并释放 claim，不产生 duplicate retry。`runStartupTerminalCleanup()` 按 `policy.terminalStates` 经 `fetchIssuesByStates` 拉取并逐 identifier 经真实 `WorkspaceManager.removeWorkspace` 清理：不做 required-label 筛选、`missing` 幂等、fetch 失败不阻止启动（§8.6）、单项 `refused` / `failed` / 异常只记诊断并继续且绝不做 `fs.rm` fallback（安全边界归 workspace 包），不复制 containment 逻辑；首个 dispatch 前的调用顺序由 M5.5 编排。

M5.5 已落地 **poll loop / startup 编排 / per-tick 失败降级 / live config re-apply / stop lifecycle**（SPEC §8.1、§14.2 / §14.3 / §14.4、§16.1 / §16.2、§6.2 / §6.3）：新增 `OrchestratorLoop`，用**单 timer 链**替代 `setInterval`——每次 tick **结束后**才按当前 effective `polling.interval_ms` 安排下一次一次性 timer，因此慢 tick 不重叠、降级出口不重复注册 timer；首次 tick 零延迟（§16.1）。每 tick 严格保持 `reconcile running → dispatch preflight → fetch active candidates → sort → dispatch until global slots exhausted`（§16.2），reconciliation **总是先执行**，即使随后 validation / candidate fetch 失败。失败降级（§14.2）：per-tick validation 失败跳过本 tick dispatch 并保留 last-known-good；candidate fetch 失败跳过本 tick、下一次 tick 重试；reconciliation refresh 失败由 authority 保留 worker。startup（§16.1 / §6.3）：初始 dispatch preflight fail-fast（失败抛 `OrchestratorStartupError`，不安排 timer、不进入调度），且 startup terminal sweep 报 **能力缺失**（缺 workspace cleanup 端口或 tracker `fetchIssuesByStates`）时同样拒绝进入调度——**实际** terminal fetch 失败 / 单项 cleanup 失败仍是 best-effort 降级、不阻止启动（§8.6）；随后 immediate first tick。live config re-apply（§6.2）：每次 tick 经注入的 `DispatchPreflightSource` 重新校验并取最新 effective（`pollIntervalMs` / `maxConcurrentAgents` / `DispatchPolicy`），经 `OrchestratorAuthority.applyEffectiveSchedulingConfig()` 原子应用；retry cap / stall timeout 继续由 authority 的 getter 从同一 effective store 读取；并发上限**下调不主动终止**已运行 worker。lifecycle（§14.3）：`OrchestratorLoop.stop()` **先同步**调用 `OrchestratorAuthority.shutdown()`（其同步前缀使全部 retry ownership 失效——含已 pop entry、仍在 `fetchIssuesByIds` 的 refresh——取消排队 retry timer、拒绝之后开启新的 workspace 删除，并立即开始以 `{ kind: "shutdown" }` 停止全部 worker），再等待 startup / 在途 tick / worker 收尾与**已开始的 workspace cleanup** 真正结束；stop 幂等、不遗留 timer、之后不再触发 tick / retry / 新 cleanup。`DispatchPreflightSource` / `CandidateIssueSource` / `PollScheduler` / `LoopDiagnostic` 全部可注入，测试用 manual timer + 可控 runner 确定性复跑；跨包端到端链路随 M5.6 收口（见下）。

## Configuration

轮询间隔、并发上限、backoff 参数等由 `@symphony/config` 产出的 typed config 提供（含 per-state 并发覆盖）；本包不自行解析 `WORKFLOW.md`。只有"当前生效"的 `pollIntervalMs` 与 `maxConcurrentAgents` 驻留在 runtime state 上；active / terminal states、required labels、per-state 并发上限、`max_retry_backoff_ms` 等由每 tick 的 effective config 以 `DispatchPolicy` / 纯函数参数传入，因此 reload 后自然采用新值。

## Extension points

- 调度 / claim / reconciliation 策略：在本包内实现，参考算法对齐 SPEC §16；
- 对 tracker / workspace / agent 的调用一律经各自公共 API；本包是唯一允许同时依赖它们的 coordination 层；
- 新增 `packages/orchestrator` 实现时同步更新 [docs/conformance.md](../../docs/conformance.md) 的 §7 / §8 / §14 行。

## Known limitations

- M5 core 与 §17.4 非 conditional 条目已收口；M6.1 snapshot 输出与同步 unavailable 已实现，获取层 timeout 尚未实现。structured logs 归 M6.2、CLI host 归 M6.3–M6.5，HTTP/dashboard 为可选扩展。外部 tracker / 真实 Codex 不在默认 Core Conformance 范围；
- retry `dueAtMs` 用单调时钟、`delay` 用注入 scheduler；测试注入手动 scheduler，不依赖真实 sleep；
- terminal retry refresh 的 workspace 清理只经注入的 `cleanupWorkspace` 端口（生产接 `WorkspaceManager.removeWorkspace`），`refused` / `failed` / 异常只记诊断并释放 claim，本包不做删除 fallback；
- worker 停止的上界由 agent 层自身的 `shutdownTimeoutMs` 与 workspace hook effective timeout 提供，本包不额外引入硬超时（避免"超时宣布退出却让 runner 继续运行"）；
- `applyAgentEvent` 只从可靠生命周期事件推进 turn 身份 / 计数，并按 thread 隔离异 thread / 异 turn 诊断事件；身份未齐时的 usage / last event 暂存在 per-attempt 遥测（`AgentTelemetryState`）中，usage 仍立即入账，因此"先到 usage、后到身份"或"身份始终未齐并最终启动失败"都不会漏账；
- runtime state 是 in-memory only（§14.3）：不提供 durable scheduler DB 或跨重启恢复，retry timer 不跨进程重启保留。

## M5.6 Core Conformance assembly

`src/workflow-integration.test.ts` 从真实文件与 `OrchestratorLoop.start()` 覆盖排序/过滤、防重复、正常和异常 retry、cap、active/non-active/terminal refresh、startup cleanup、stall、slot exhaustion、遥测与 valid → invalid → recovered 文件配置。`src/workflow-shutdown.test.ts` 在真实 worker 与 filesystem 上验证 stop 的在途屏障。`src/boundaries.test.ts` 用 TypeScript AST 检查生产 import/export/dynamic import 只经 public API，并锁住 runtime dependency 方向；orchestrator 不解析 raw Codex JSON。

宿主接线示例见 `src/workflow.test-helpers.ts`：使用 registry 的 extension 加载 effective workflow，校验非空 codex.command，成功才提交整套配置与 adapter；profile 默认 states 由注册表 profile 提供，不要求 config 层回写。candidate/refresh/startup sweep 共享同一 adapter；attempt 使用真实 `runAgentAttempt`；路径与删除经真实 `WorkspaceManager`。M6 应消费这些既有 public ports，不重写 scheduler semantics。配置与生命周期 policy 见 [Agent Note](../../notes/accepted/architecture/2026-10-03-orchestrator-core-conformance.md)。

运行 `npm test -w @symphony/orchestrator`；13 项 §17.4 映射见 [conformance](../../docs/conformance.md#174-orchestrator-core-conformance)。两项 conditional snapshot 验收中，running/retry/token/rate-limit 输出投影与同步 unavailable 已由 M6.1 实现；获取层 timeout 尚未实现，本地同步入口不适用，因此 timeout/unavailable 合并项未全部完成。snapshot 证据及边界见 [conformance 的 §17.6 分项](../../docs/conformance.md#176-分项证据m61)；structured logging、CLI host 和可选 HTTP/dashboard 仍属后续工作。

## M6.1 snapshot metadata

`RetryScheduleRequest.issueUrl?: string | null` 最小透传到 retry；worker outcome 用最新 running issue URL，refresh 失败保留原值，slot/dispatch 失败重排用 refreshed URL（含显式 null）。不保存完整 Issue、不增加 metadata cache、不改变 M5 policy/timer ownership。snapshot 从当前 state 读取，monotonic clock 必须与 authority 同源；observability 仅作为 devDependency 用于 `src/observability-integration.test.ts`。见 [snapshot Note](../../notes/accepted/architecture/2026-10-03-observability-snapshot.md)。
